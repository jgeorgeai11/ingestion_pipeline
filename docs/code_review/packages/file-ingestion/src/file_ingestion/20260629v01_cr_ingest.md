## Implementation Plan

1. [pending] `max_pages_per_batch` config value is read with no type or range validation — `code/file_ingestion/ingest.py`
   - 1.1. [major] Line 702: `max_pages_per_batch = parse_cfg.get("max_pages_per_batch", DEFAULT_MAX_PAGES_PER_BATCH)` reads the run-level config value with no coercion to `int` and no non-negative check, then threads it untouched through `step_parse` (line 749) into `parse_files_docling` and on to `_convert_document`, where the only guard is the bare comparison `max_pages_per_batch <= 0`. The default (25) and any author-supplied int work, but every other TOML type fails — and the three failure modes are not symmetric:
       - **Negative int (e.g. `max_pages_per_batch = -5`) silently disables batching.** `-5 <= 0` is `True`, so `_convert_document` takes the single-pass path with no log and no error — defeating the exact OOM/over-commit protection this feature exists to provide. This is the most insidious mode: it fails open and quiet, so a typo'd config parses large PDFs single-pass and may OOM/crash the parse with nothing pointing back to the misconfiguration.
       - **String (e.g. `max_pages_per_batch = "25"`) raises an uncaught `TypeError`** at the `max_pages_per_batch <= 0` comparison (str vs int), for PDF inputs (the `suffix != ".pdf"` term short-circuits non-PDFs first). This is a hard crash, not the clean "Invalid config value" exit.
       - **Float (e.g. `max_pages_per_batch = 2.5`) raises an uncaught `TypeError`** in `range(1, n_pages + 1, batch)` inside `_page_range_slices` (float step), again PDF-only.
     Contrast with the sibling `pdf_backend` setting, which IS validated: an invalid backend raises `ValueError` from `parse_files_docling`, propagating to `main()`'s `except ValueError` handler (line 720) as a clean "Invalid config value" + `sys.exit(1)`. `max_pages_per_batch` has no equivalent guard, so a misconfiguration either crashes with a raw traceback or silently neuters the feature. This violates the python-development Data Validation skill (validate inputs, including config inputs). Fix in-file at line 702: coerce and validate the value (require a non-negative int), raising `ValueError` on a bad value so the existing handler at line 720 reports it as "Invalid config value" and exits cleanly. Example:
        - Current (line 702):
          ```python
          max_pages_per_batch = parse_cfg.get("max_pages_per_batch", DEFAULT_MAX_PAGES_PER_BATCH)
          ```
        - Expected (validate it is a non-negative int; let the bad-value path hit the line-720 handler):
          ```python
          max_pages_per_batch = parse_cfg.get("max_pages_per_batch", DEFAULT_MAX_PAGES_PER_BATCH)
          if not isinstance(max_pages_per_batch, int) or isinstance(max_pages_per_batch, bool) or max_pages_per_batch < 0:
              raise ValueError(
                  f"[parse].max_pages_per_batch must be a non-negative int, got {max_pages_per_batch!r}"
              )
          ```
       (Note: the downstream crash/silent-disable in `_convert_document`/`_page_range_slices` is cited only as the consequence — `file_parser.py` is out of scope; the missing guard is here at ingest.py:702.)

2. [pending] No config TOML documents a tighter constraint than "non-negative int" — `code/file_ingestion/ingest.py` (cross-file note)
