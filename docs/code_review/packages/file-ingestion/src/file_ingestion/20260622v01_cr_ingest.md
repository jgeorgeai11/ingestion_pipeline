## Implementation Plan

1. [completed] Config consistency — `code/file_ingestion/ingest.py`
   - 1.1. [minor] Line 530 vs 403: `main()` builds `document_titles` with `d["title"]`, which raises `KeyError` (caught at 555, exit 1) when a document entry omits `title` — i.e. `title` is effectively **required**. But `step_load` reads it with `document_titles.get(file_name, file_name)` (line 403), whose `file_name` default implies `title` is **optional**. The two halves of the same file disagree on whether `title` is required; the `step_load` default is dead code under the current `main()`. Pick one contract: either make `title` optional in `main()` (so the `step_load` default can fire) or drop the unreachable default in `step_load` and document `title` as required.
        - Current (line 530):
          ```python
          document_titles = {d["file"]: d["title"] for d in documents}
          ```
        - Expected (if title is optional — aligns with step_load's default):
          ```python
          document_titles = {d["file"]: d.get("title", d["file"]) for d in documents}
          ```

   - 1.2. [minor] Lines 528-530, 540-541: All per-document maps (`collection_paths`, `document_titles`, `do_ocr_map`, `pdf_backend_map`) are dict comprehensions keyed on `d["file"]`. If two document entries share the same `file` value (e.g. the same source filename authored to two different `collection_path`s), the later entry silently overwrites the earlier in every map and only one is ever loaded — no warning, exit 0. This is a fail-silent shape (exception-handling skill #4). Given the module keys document identity on `collection_path` (not filename) this duplicate-filename case is plausible. Detect duplicate `file` values and fail fast (or warn) rather than collapsing silently.

   - **RESOLVED (1.1):** title kept **required**. The dead optional default in `step_load` was removed (`document_titles.get(file_name, file_name)` → `document_titles[file_name]`); `main()` unchanged. **RESOLVED (1.2):** `filter_valid_documents` now detects duplicate `file` values across all input documents and raises `ValueError` (fail-fast).

2. [completed] Connection handling — `code/file_ingestion/ingest.py`
   - 2.1. [minor] Lines 81-82: `get_engine` interpolates `user` and `password` directly into the connection URL. A password containing URL-reserved characters (`@`, `:`, `/`, `?`, `#`, etc.) corrupts the URL and yields a confusing connection error rather than a clean auth failure. Use `sqlalchemy.URL.create`, which percent-encodes credentials safely.
        - Current:
          ```python
          conn_str = f"postgresql://{user}:{password}@{host}:{port}/{db_name}"
          return create_engine(conn_str)
          ```
        - Expected:
          ```python
          from sqlalchemy import URL
          url = URL.create(
              "postgresql",
              username=user, password=password,
              host=host, port=int(port), database=db_name,
          )
          return create_engine(url)
          ```

   - **RESOLVED (2.1):** `get_engine` now builds the URL with `sqlalchemy.URL.create` (credentials percent-encoded), matching the MCP server pattern.

3. [completed] Transaction boundaries — `code/file_ingestion/ingest.py`
   - 3.1. [minor] Lines 413-421 vs 430: The existence check runs in its own `engine.connect()` (autocommit read) **outside** the `engine.begin()` write transaction that performs the delete+insert. The delete+insert itself is correctly atomic (a failed reinsert rolls back the delete, and content cascades), which is good. But the read-then-write straddles two connections: between the `SELECT` and the `begin()` block a concurrent writer could insert/delete the same `collection_path`, so the skip/overwrite decision can act on stale state (a non-overwrite insert would then hit a PK violation; an overwrite delete targets a row that may already be gone). Risk is low in the intended single-process pipeline, but folding the `SELECT ... FOR UPDATE` (or simply the existence read) into the same `engine.begin()` block removes the gap and keeps the whole per-document decision in one transaction.

   - **RESOLVED (3.1):** the existence `SELECT` was folded into the same `engine.begin()` block as the delete+insert, so each per-document decision is one transaction (the non-overwrite skip `continue`s out, committing an empty transaction). No `FOR UPDATE`.

4. [completed] Edge cases — `code/file_ingestion/ingest.py`
   - 4.1. [suggestion] Lines 528-529, 595: If `filter_valid_documents` drops *every* document (all `collection_path`s missing/blank/invalid), `documents` and `file_paths` are empty, all three steps iterate over nothing, and `main()` logs `SUCCESS: Pipeline complete for 0 files` and exits 0. This is the same fail-silent shape (exception-handling skill #4) the prior review's [critical] cared about, one level up: a config in which nothing is ingestable reports success. Consider failing fast (or at least WARNING) when `not documents` while `all_documents` was non-empty, so a wholly-invalid config is visible in the exit code.
   - **RESOLVED (4.1):** `main()` now raises `ValueError` (exit 1) when `all_documents` was non-empty but every document was dropped. Chose **fail** over warn.
