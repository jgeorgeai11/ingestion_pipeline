## Implementation Plan

1. [pending] Correctness / error handling — `code/file_ingestion/ingest.py`
   - 1.1. [critical] Lines 266-269: A missing parsed JSON is logged and skipped with
     `continue`, so the file is silently never cleaned yet `main()` still reports `SUCCESS`
     and exits 0. This violates the exception-handling skill's "Fail fast — don't silently
     swallow errors" and is inconsistent with `step_load`, which raises `FileNotFoundError`
     for the exact analogous missing-input case in the same file. The inconsistency compounds
     within `step_clean` itself: a *missing* source skips one file and continues (exit 0),
     while a *malformed* source makes `parse_docling_json` raise `ValueError`, which aborts
     the whole loop so every file after it is never processed (exit 1). Two bad inputs thus
     produce opposite blast radii and opposite exit codes. Decide a single failure policy for
     the step — accumulate-and-raise-once (as `step_parse` does) or fail-fast (as `step_load`
     does) — and apply it to both the missing-file and malformed-file paths.
        - Current:
          ```python
          parsed_json_path = parsed_dir_path / json_filename
          if not parsed_json_path.exists():
              logger.error(f"Parsed JSON file not found: {parsed_json_path}")
              continue
          ```
        - Expected (fail-fast option, to match `step_load`):
          ```python
          parsed_json_path = parsed_dir_path / json_filename
          if not parsed_json_path.exists():
              raise FileNotFoundError(
                  f"Parsed JSON not found in {parsed_dir}: {json_filename}"
              )
          ```
          (or collect per-file failures and raise a single combined error after the loop,
          mirroring `step_parse`; either way the exit code must reflect the failure.)

   - 1.2. [major] Lines 273-279: When `parse_docling_json` returns an empty list, the step
     logs a warning but still writes a non-empty JSON file (`{"n_parsed_sections": 0,
     "sections": []}`). Because the skip-sentinel only checks `st_size > 0` (lines 258-262),
     this zero-section output is treated as "already done" on the next non-overwrite run and
     is never re-cleaned even after the underlying parse is fixed. A genuinely empty parse
     becomes sticky. Either skip writing when `not sections`, or make the skip-sentinel
     aware that `n_parsed_sections == 0` is not a satisfied output.
        - Current:
          ```python
          sections = parse_docling_json(parsed_json_path)
          if not sections:
              logger.warning(f"No sections parsed from {json_filename}")

          record = sections_to_record(sections)
          cleaned_json_path.write_text(...)
          ```
        - Expected (one option — do not persist an empty result):
          ```python
          sections = parse_docling_json(parsed_json_path)
          if not sections:
              logger.warning(f"No sections parsed from {json_filename}; not writing output")
              continue
          ```

   - 1.3. [minor] Lines 277-279: `cleaned_json_path.write_text(...)` can raise `OSError`
     subclasses other than `FileNotFoundError` (e.g. `PermissionError`, disk-full
     `OSError`). The docstring correctly declares `OSError` is raised, but `main()`'s
     specific catch tuple is `(FileNotFoundError, ValueError, RuntimeError)` (line 523), so a
     write failure falls through to the broad `except Exception` (line 527) and is logged as
     an "unexpected error" rather than a clean pipeline failure. The exit code is still 1, so
     this is cosmetic, but the message misclassifies a known, declared failure mode. Add
     `OSError` to the specific catch in `main()`.
        - Current (line 523):
          ```python
          except (FileNotFoundError, ValueError, RuntimeError) as e:
          ```
        - Expected:
          ```python
          except (FileNotFoundError, OSError, ValueError, RuntimeError) as e:
          ```
          (`FileNotFoundError` is a subclass of `OSError`; listing both is harmless and keeps
          intent explicit, or list `OSError` alone.)

2. [pending] Readability — `code/file_ingestion/ingest.py`
   - 2.1. [suggestion] Line 281: The success log reads `record['n_parsed_sections']`,
     re-deriving a value already available as `len(sections)`. This couples the log line to
     the exact dict key produced by `sections_to_record`. Using `len(sections)` is
     equivalent, avoids the key dependency, and reads more directly.
        - Current:
          ```python
          logger.info(
              f"Wrote cleaned JSON: {cleaned_json_path} ({record['n_parsed_sections']} sections)"
          )
          ```
        - Expected:
          ```python
          logger.info(
              f"Wrote cleaned JSON: {cleaned_json_path} ({len(sections)} sections)"
          )
          ```
