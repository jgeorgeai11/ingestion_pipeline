## Implementation Plan

1. [completed] Complete the config key-collision detection in `filter_valid_documents` - `code/file_ingestion/ingest.py`
   - 1.1. [major] Lines 148-179: duplicate `collection_path` values across documents are not detected, so one document is silently dropped and still reported as a success. `filter_valid_documents` fails fast on a repeated `file` (lines 148-156) because the per-document maps are keyed on it, but `collection_path` is the document primary key in `document` (`sql/schema.sql` line 20) and is equally collision-prone in an authored TOML. With two entries sharing one `collection_path`: the first inserts; the second reaches `step_load`, its existence SELECT (lines 555-562) finds the row just written, and the `existing and not overwrite` branch logs "already ingested", appends the file to `loaded_ok` (line 569) and continues — so `main()` counts it as loaded, reports `SUCCESS`, and exits 0 while the second document's content was never ingested. Under `overwrite=True` the second entry deletes and replaces the first, and again both count as loaded. The same fail-fast reasoning already applied to `file` applies here.
        - Current: only `file` is checked for duplicates (`if file_name in seen: dupes.add(file_name)`), and `collection_paths[file_name] = valid_path` (line 179) silently accepts a repeated value.
        - Expected: after validation, detect repeated `collection_path` values and raise, e.g. `if valid_path in collection_paths.values(): raise ValueError(f"Duplicate collection_path in config: {valid_path}")` (or collect and report all duplicates at once, matching the `file` check's "name every offender" style). The `ValueError` propagates to `main()`'s config handler (line 745) as a clean "Invalid config value" exit.
        - Resolution: Implemented with the collect-and-report-all variant. A `seen_paths`/`path_dupes` set pair accumulates validated paths inside the keep loop (`O(n)` rather than the `in collection_paths.values()` scan), and after the loop `raise ValueError(f"Duplicate collection_path(s) in config: {sorted(path_dupes)}")` names every offender in the `file`-check style. Only KEPT documents participate: a document dropped for an invalid `collection_path` is excluded from the run and so cannot collide — this scoping is stated in the docstring and pinned by `test_duplicate_collection_path_ignored_when_one_is_skipped`. The function docstring's Raises section and the module docstring now document the fail-fast identity rules.
   - 1.2. [minor] Lines 148-156: the duplicate check keys on the full filename, but every downstream artifact is keyed on `Path(file_name).stem` (lines 292, 305, 340, 401, 531) as the module docstring states (lines 11-12). Two entries whose filenames differ only by extension (`ge101c01.pdf` and `ge101c01.docx`) pass the duplicate check, then collide on `parsed_dir/ge101c01.json` and `cleaned_dir/ge101c01.json`: the second parse overwrites the first, and both documents load the *same* cleaned content under two different `collection_path` values — wrong data, ingested silently. No current config in `config/` contains such a pair, so this is preventive.
        - Current: `if file_name in seen:` — compares `"ge101c01.pdf"` vs `"ge101c01.docx"` and sees no duplicate.
        - Expected: check the artifact key that actually collides, e.g. `stem = Path(file_name).stem` accumulated in `seen`/`dupes` (reporting the offending filenames), since the stem is what names every parsed/cleaned output.
        - Resolution: Implemented by replacing the `seen`/`dupes` filename sets with a `stem_files: dict[str, list[str]]` grouping (stem -> the filenames using it); every filename in a group of more than one is reported, so the raised message names each offender (`['a.docx', 'a.pdf']`). Verified against all 36 configs under `code/file_ingestion/config/`: none trips the new guard.
