## Implementation Plan

1. [completed] Survivor computation masks a re-parse failure under overwrite — `code/file_ingestion/ingest.py`
   - 1.1. [major] Lines 290-313 (esp. 308-313): `step_parse` discards `parse_files_docling`'s return value (the list of files that converted AND exported successfully — `file_parser.py:210,219`) and instead recomputes survivors purely by inspecting the JSON on disk (`json_path.exists() and json_path.stat().st_size > 0`). Under `overwrite=True` this silently masks a re-parse failure. Trace: (a) `overwrite=True` -> the skip block at line 263 is bypassed, `file_paths` stays the full list; (b) a file X that already has a JSON from a prior run fails re-conversion -> `parse_files_docling` raises `RuntimeError`, caught at line 295 into `group_failures`; (c) on `converter.convert` failure `out_file` is never touched (`file_parser.py:182-186`), and on an export failure `_export_atomic` deletes only the temp file and leaves the old output in place (`file_parser.py:268-272`) — so X's STALE JSON is still on disk, non-empty; (d) the survivor loop at lines 308-313 sees X's stale JSON, appends X to `parsed_ok`, and records NO failure. Result: a re-parse failure under `overwrite` is reported as a successful parse, the run can exit 0, and the stale parsed JSON flows on to clean/load — a silent loss in exactly the "no silent loss" guarantee the resilient design exists to provide. `overwrite` is reachable (`config.get("overwrite", False)`, line 643). Contrast: `step_clean` (line 412) and `step_load` (line 595) build their ok-lists from successful in-loop processing, so they do not have this gap; only `step_parse` infers survivors from disk. Fix: compute survivors as the union of (files skipped because their JSON already existed) and (the successes returned by `parse_files_docling`), rather than from a raw disk scan — so a file whose re-conversion failed is recorded as a failure even when a stale output is present.

2. [completed] Per-file failure attribution in step_parse — `code/file_ingestion/ingest.py`
   - 2.1. [minor] Lines 305, 313: `step_parse` computes a single shared `reason = "; ".join(group_failures) or "parsed JSON output missing or empty"` once and attaches that same string to EVERY failed file (line 313), regardless of which group the file belonged to. A file whose own group converted cleanly but whose JSON is absent for an unrelated reason gets the concatenation of all groups' errors; conversely a file from a failing group and a file with simply-missing output are indistinguishable. Failure attribution is imprecise. Consider keying the per-group `RuntimeError` to that group's files (e.g. record a `dict[file -> reason]` over `group_files`), falling back to the generic "parsed JSON output missing or empty" for files in no failing group. (Carried forward from `20260622v02` finding 1.2; still present.)

3. [completed] Duplicate ERROR logging of each failure — `code/file_ingestion/ingest.py`

[minor] Lines 414, 601 vs 756-759: each per-file failure is logged at ERROR twice — once inside the library step (`step_clean` line 414 "Clean failed for ..."; `step_load` line 601 "Load failed for ...") and again in `main()`'s summary loop (lines 756-759). The logging skill (#5, "avoid duplicate logging — if a library module logs details, the entry script shouldn't repeat them") cautions against exactly this. The consolidated end-of-run summary is defensible (it co-locates every failure after survivors are threaded), but emitting the same `file`/`reason` at ERROR from both layers is a genuine duplication. Consider demoting the summary-loop per-failure lines to DEBUG (or the per-step lines to WARNING) so a reader sees each failure once at ERROR.
