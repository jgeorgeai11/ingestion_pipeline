### Verified correct (general correctness, no issue)

- `make_collection_path` derive/validate: the `override` path is validated unchanged (never rewritten), and a derived `f"{stem}.{leaf}"` is itself passed through `validate_collection_path`. A degenerate stem or sheet (no alphanumerics) yields an empty label, producing `.leaf` or `stem.`, which fails `validate_collection_path` loudly. Verified on disk: `make_collection_path("file.xlsx", "###")` and `("###.xlsx", "Sheet")` both raise `ValueError`. The function always yields a valid lowercase ltree or fails loudly.
- `_ltree_label` sanitization: lowercases, collapses non-`[a-z0-9]` runs to `_`, strips leading/trailing `_`; a leading digit is permitted (matches the `_LTREE_RE` label class). It can return empty, but that empty is caught by the downstream `validate_collection_path` in `make_collection_path` (the only caller), so no invalid ltree escapes.
- Identifier-length cap: `normalize_column_name` caps to `MAX_IDENTIFIER_LENGTH` then `rstrip("_")` so the generated name equals what Postgres would store (no silent-truncation mismatch). `_suffixed` reserves room for the `_<n>` suffix before slicing and rstrips, keeping `base_<n>` within the cap. Verified the cap math on 63+ char inputs.
- `compute_source_hash`: returns `int(sha256_hexdigest, 16) & 0xFFFFFFFFFFFFFFFF`, an unsigned 64-bit value in `[0, 2^64)`. This exactly matches the `excel_schema.sql` column `source_binary_hash numeric(20,0)` with `check (>= 0 and < 18446744073709551616)`, and the documented file_ingestion convention (`low 64 bits of sha256(source bytes)`, an unsigned 64-bit integer; `file_ingestion/sql/schema.sql` uses the identical `numeric(20,0)` + uint64 CHECK). No signed-`bigint` overflow risk. The empty-list case hashes the empty string deterministically; callers skip empty sheets upstream, so it is never persisted.
