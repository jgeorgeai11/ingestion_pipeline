## Implementation Plan

1. [completed] Close the PUBLIC-derived write paths behind the stated read-only guarantee - `code/grants/mcp_ro_policy.sql`
   - 1.1. [major] Lines 79-80: PostgreSQL grants `TEMPORARY` on a database to PUBLIC by default (and, on server versions before 15, `CREATE` on schema `public`). Only PUBLIC's `CONNECT` is revoked here, so `mcp_ro_policy` inherits the ability to `create temp table ... as select ...` — and, pre-15, to create and write real tables in `public`. That contradicts the file header's central claim (lines 7-9: "the role holds SELECT and nothing else, so run_sql cannot write no matter what SQL a client sends"), which is the guarantee this file exists to enforce.
        - Current: `revoke connect on database :"database" from public;`
        - Expected: `revoke connect on database :"database" from public;` followed by `revoke temporary on database :"database" from public;` and `revoke create on schema public from public;`, with a comment stating that these close the two write paths PUBLIC grants by default so the SELECT-only model is actually DB-enforced
        - Resolution: Implemented with an added accommodation — added both revokes after the CONNECT revoke, with a why-comment naming each write path (`create temp table ... as select ...` via database TEMPORARY; pre-15 real tables via CREATE on schema `public`), and updated the header's privilege-model line to list all three PUBLIC revokes. The accommodation: `revoke create on schema public` names schema `public` unqualified, so a database that has already dropped that schema now aborts the run, which finding 3.1's transaction turns into a clean no-op rather than a partial apply; documented as a new `Preconditions:` bullet ("Schema public still exists — the stock default") instead of guarding the statement, so the hardening stays a flat REVOKE rather than a conditional block. Verified live 2026-08-17 against `policy_db` as `policy_db_maintainer` (psql 18): the finding was real on the live server — `has_database_privilege('public','policy_db','TEMPORARY')` was TRUE before, so `mcp_ro_policy` could create temp tables; after applying, both it and `has_database_privilege('mcp_ro_policy',...,'TEMPORARY')` are FALSE. `has_schema_privilege('public','public','CREATE')` was already FALSE (PostgreSQL 15+ default), so that second revoke is a no-op on this server and is hardening for pre-15 or re-granted deployments.

2. [completed] Make the target database unambiguous - `code/grants/mcp_ro_policy.sql`
   - 2.1. [minor] Lines 66-69, 79-92: the database-level statements target the `:database` variable while the schema-level statements target whatever database the connection is on, and nothing checks that the two agree. An invocation such as `-v database=policy_db -d other_db` revokes/grants CONNECT on `policy_db` and then applies USAGE/SELECT inside `other_db` (or aborts mid-script if the schemas are missing there), splitting the privilege model across two databases with no error. Deriving the name from the live connection makes the mismatch impossible rather than merely detectable, and matches the fix proposed for the sibling `database_description.sql` (see `cr_20260816v01_database_description.md`, finding 3.1), which parameterizes `database` the same way.
        - Current: `\if :{?database}` / `\else` / `    \set database policy_db` / `\endif`
        - Expected: `select current_database() as database \gset` (with a comment noting the schema grants apply to the connected database, so the database name is taken from the connection), and the header's invocation line simplified to drop `-v database=policy_db`
        - Resolution: Implemented as specified — replaced the `\if :{?database}` block with `select current_database() as database \gset` plus a why-comment, and dropped `-v database=policy_db` from the invocation. Also updated two now-stale header lines that named `database` as a variable (the "Invocation" preamble and the schema-defaults comment), and added to the `Preconditions:` block that the script runs while connected to the target database. The sibling `database_description.sql` took the identical `\gset` form (see `cr_20260816v01_database_description.md`, finding 3.1).

3. [completed] Fix apply-time atomicity and header accuracy - `code/grants/mcp_ro_policy.sql`
   - 3.1. [minor] Lines 47-49: each statement autocommits, so `ON_ERROR_STOP` stops the run but leaves the statements already executed in place — e.g. PUBLIC's `CONNECT` revoked and `cms_iom` granted while `qpp_cm`/`usc` are not. GRANT, REVOKE, and ALTER DEFAULT PRIVILEGES are all transactional in PostgreSQL, so the whole model can be applied as a unit.
        - Current: `\set ON_ERROR_STOP on`
        - Expected: `\set ON_ERROR_STOP on` plus an explicit `begin;` before the first `revoke` and `commit;` after the last `alter default privileges` (or a documented `--single-transaction` in the invocation line), with the header comment updated to say the model is applied all-or-nothing
        - Resolution: Implemented as specified via the in-file form (not `--single-transaction`), so atomicity holds no matter how the file is invoked: `begin;` after the `\gset` and before the first `revoke`, `commit;` after the last `alter default privileges`, with a comment naming the concrete half-applied state it prevents, plus a new `Preconditions:` bullet stating the model applies all-or-nothing. The `\gset` sits outside the transaction deliberately — it only reads `current_database()`. Verified live 2026-08-17: the rewritten script runs clean end to end as `policy_db_maintainer` (BEGIN, 3 REVOKEs, 7 GRANTs, 3 ALTER DEFAULT PRIVILEGES, COMMIT; exit 0), and `mcp_ro_policy`'s served privileges are unchanged pre/post — CONNECT plus USAGE and SELECT on `cms_iom`/`qpp_cm`/`usc`, with INSERT still denied — so the `\gset` parameterization and the transaction wrapper render correctly against the real server.
   - 3.2. [minor] Lines 42-45: the precondition states flatly that "there is no REVOKE-before-GRANT", which line 79 contradicts — PUBLIC's `CONNECT` is revoked every run. The intended claim is that none of *this role's own* grants are revoked first; as written it misleads a reader auditing what the script takes away.
        - Current: `--   * Grants are additive and idempotent: there is no REVOKE-before-GRANT,`
        - Expected: `--   * Grants are additive and idempotent: nothing this role already holds is` / `--     revoked first (the only REVOKE targets PUBLIC's default CONNECT),`
        - Resolution: Implemented with one wording deviation — the parenthetical reads "(the only REVOKEs target PUBLIC's defaults)" rather than naming CONNECT alone, because finding 1.1 added two further PUBLIC revokes (TEMPORARY and CREATE on schema `public`) in the same pass; naming CONNECT only would have reintroduced the same inaccuracy this finding fixes.
