## Key Data Decisions and Considerations

1. Engine/instance boundary — the engine is source-agnostic (parse, clean, load, embed anything a config names); the instance is everything that knows what the sources and targets are (corpus configs, source-specific downloaders, grants, contract, credentials). This is why `data_acquisition` moves: it is a module per source, not a generic downloader, and a new instance would reuse the pipeline modules untouched while needing entirely new acquisition code.
2. The bare `.env` is removed rather than renamed because the concept it encoded ("this repo's default database") no longer exists once engine and instance are separated. Credentials belong to whoever a run is for: production runs are for an instance (per-instance env files), test runs are for the engine's own verification (`.env.test`), and nothing is for "the engine in general" — an engine-level default would only ever be exercised as a fallback by a run that forgot to name its credentials, which is exactly the ambient-credentials bug class `code/lib/env.py` exists to remove.
3. Removing the default dotenv search reverses a deliberate decision from `docs/activities/lib/20260818v01_add_env_file_flag.md` (decision 2, "no existing invocation changes"). That decision preserved compatibility with a world that had a legitimate repo-wide default; this activity abolishes that world, so the compatibility argument no longer applies. The cost is that every invocation now carries `--env-file`; the benefit is that a forgotten flag is a usage error instead of a silent connection to whatever the search found.
4. `archive_db_rag` integration is out of scope: that repo — and the gitignored `.env.archivedb` file — exist only on the machine running that workflow, not here (this repo carries only the `.gitignore` entry, added in commit `cdda260`). Nothing on this machine changes for archive_db; on that machine, flag-based runs with `--env-file .env.archivedb` keep working since the flag path is untouched. Follow-up activity when that repo is at hand: fold it in as `instances/archive_db/` (its configs and env file), at which point `.env.archivedb` retires.
5. Test-role least privilege — the `ephemeral_schema` fixture currently runs as `policy_db_maintainer` against the production `policy_db` database, protected only by UUID schema names. `ingestion_test_runner` owning a dedicated `ingestion_test` database makes the protection structural: the role has no rights on any real database, so a buggy test cannot touch the corpus. The provisioning SQL lives in engine territory (`code/testing/`), not the instance's `grants/`, because the test database serves the engine's suite and must survive an eventual engine/instance repo split.
6. The annotated `example.toml` files stay in the engine because they document the config schema each module accepts — engine interface documentation — while every real corpus config moves to the instance. `ingest_test_document.toml` moves with the instance configs because it loads into `policy_db` (collection path `cms_iom.test.*`); retargeting the smoke ingest at `ingestion_test` would decouple it from the instance entirely and is a candidate follow-up, not part of this activity.
7. Split-readiness invariants this layout establishes (a future engine/instance repo split reduces to a `filter-repo` carve if these hold): the engine never references `instances/` (task 10.2 makes it grep-able); instance code consumes the engine only via its CLIs, with `code/lib` as the one known cross-boundary import (acquisition imports `logconfig`), remedied at split time by vendoring per the established precedent; engine tests need no instance credentials (Phase 1); the directory layout is settled in one move (task 3.3). The one-move rule exists because `git filter-repo` path-carving loses `--follow` history across renames — observed in the repo split (task 15.5 of `docs/activities/repo-split/20260813v01_split_rag_into_two_repos.md`), where `file_ingestion` history stops at the `pdf_ingestion` rename — so every later reshuffle across the engine/instance boundary would degrade what a future carve can preserve.
8. Deliberately deferred: config-internal data paths (`source_dir = "data/input/..."`) remain CWD-relative, so runs still start from the repo root, and the gitignored `data/` and `logs/` directories stay at the repo root. The same deferral covers the hardcoded CWD-relative `setup_logging(log_dir="logs/...")` calls throughout the entry points and validators, including the test modules that call `setup_logging` at import time and so create a `logs/` tree in whatever directory pytest is invoked from (e.g. `excel_ingestion/unit_tests/test_utils.py:14`, `test_download_usc_titles.py:20`). Re-anchoring all of these is the remaining split-readiness gap and belongs to a follow-up activity — it touches every config and all six entry points' path resolution, and nothing in this activity depends on it.
9. This activity produces no new data tables, so per-table `data_val_*` outputs do not apply (precedent: the repo-split activity, decision 10). The outputs under test are behavioral: the suite passing from any CWD, the smoke ingest with explicit credentials, and the flag-less usage errors (tasks 10.1-10.4).
10. Both the local PostgreSQL server (for task 1.5 and the smoke ingest) and superuser access (to create the role and database) are available on this machine per the current `.env`, which carries both credential sets today.
11. Tasks 2, 4, and 8 each touch more than one code file, deviating from the one-code-file-per-task rule (precedent: repo-split activity, decision 7). In each case the edit is a single mechanical substitution repeated across near-identical files — task 2 replaces `policy_db` with `ingestion_test` at the named live-connection sites, task 4 relocates one module and re-verifies its `parents[N]` inserts, task 8 flips the same argparse flag to required in the six entry points — so per-file tasks would obscure rather than clarify; every affected file is still named in a subtask.
