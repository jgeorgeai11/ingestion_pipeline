goal: Fix two defects in the `python-development` skill's logging resources, both of which propagate into every project scaffolded from them. `setup_logging` defaults to `overwrite=True` while `RunTimestampFilter`'s docstring says it exists so that "one appended log file [can] separate its runs" — a mechanism and a default describing two different designs, and the truncating one silently destroys the log of a failed run when it is retried. ## Key Data Decisions and Considerations

1. **The logging resources are fixed at the source, and this activity goes no further than them.** `logconfig.py` is a template copied into a project when it is scaffolded, so a defect in it is reproduced by every later copy and fixing any single copy leaves the template still seeding it. The two defects here — the retention contradiction and the naive timestamps — are both in the template itself, which is why the fix belongs at this level. Scope is strictly the skill's own files: two of them, named in tasks 1 to 3, with task 4 verifying only that the skill is internally consistent afterwards.
2. **Appending becomes the default rather than the guidance saying "consider appending".** Three options were weighed. Keeping `overwrite=True` and softening `RunTimestampFilter`'s docstring resolves the contradiction in the wrong direction: the run-separating mechanism would then exist for a case the default never produces, and the failure mode stays. Keeping the default and documenting the choice relies on every future entry point remembering to pass the flag, which is the same "convention, not enforcement" weakness that let the contradiction survive this long. Flipping the default makes the shipped behaviour match the shipped mechanism, and its blast radius is small because the template is COPIED into projects rather than imported — existing copies keep their current behaviour until deliberately re-aligned. The observed cost of the current default is concrete: a multi-hour batch run failed, was retried, and the retry truncated the failed run's log before it could be read.
3. **The `Z` marker is what makes the two timestamp forms safe to mix.** Task 1 makes appending the default and task 2 changes the timestamp reference, so a file written across both changes can legitimately hold local-time records followed by UTC ones. Neither form carries a zone otherwise, so an ordering read across that boundary would be silently wrong by whatever the host's offset is. The marker costs one character and makes the discontinuity visible.
4. **No rotation, size cap, or pruning is added.** Appending grows a file without bound, which is the honest cost of this change. Bounding it is a project-level decision — how long evidence is worth keeping, how much disk a log may take, whether an operator prunes by hand — and a template that imposed one policy would be wrong for most of the projects that copy it. The guidance names the trade so a project can decide; it does not decide for it.
5. **The skill ships no test suite, so task 4.3 is the verification.** `scripts/logconfig/` holds `logconfig.py` and `__init__.py` and nothing else, with no tests beside them. A behaviour change to a default therefore has to be proved by running the module — two appended runs producing two distinct marked timestamps, and one truncating run producing one — rather than by a test that does not exist. Adding a suite for the skill's scripts would be worth doing and is deliberately out of scope here.
6. **This activity produces no data file or table, so it carries no data-validation tasks.** Everything it changes is one Python module and one guidance document. What is verified is the module's runtime behaviour (task 4.3) and the internal consistency of the skill's own statements about it (4.1, 4.2).

The ignore is the same fact the vendored copy's docstring records — CI cannot depend on untracked `.claude/` content — so it is expected rather than a problem to fix here.
