## Key Data Decisions and Considerations

1. Descriptions are DDL and ride with the code that creates the object — `metadata_db`'s established pattern (`0001_initial_schema.sql` ends in a `comment on table` block; per-instance schema comments are a config knob applied by `apply_ddl.py`). The current `pg_metadata/*_descriptions.sql` files are after-the-fact patches: a fresh ingest into a new schema produces undescribed tables until someone remembers the side file.
2. The template/config split follows what varies: structural text (what the table IS) is identical for every corpus and belongs in the DDL template; per-corpus flavor (the schema description, qpp_cm's MIF wording, usc's statutory wording) varies per config and belongs in TOML, mirroring `apply_ddl.py`'s `schema_comment` knob. Only cms_iom's table comments are the generic text; qpp_cm AND usc carry flavored document/content texts and so both get table-level overrides (usc's flavor — "ltree encoding the title number and chapter range", "statutory text" — would otherwise be silently replaced by the generic template on the next ingest, since comment application is unconditional). The one flavored text deliberately dropped is usc's embedding-table comment ("Embedded chunks ... for semantic similarity search"): it predates the hybrid model and understates the table (it does carry `chunk_tsv`), so the generic default replaces it — landing when the usc embedding config next re-runs (task 8.5's sweep). The default is conditional on `header_columns` (task 7.1) so it never claims a header prefix the config doesn't produce; all three live embedding configs set `header_columns`, so the cms_iom/qpp_cm texts are preserved verbatim.
3. Grants deliberately do NOT ride per module, though descriptions do. `metadata_db`'s `grants/` convention is one file per role holding its complete privilege model — the file is the DB-enforced backing of the server's read-only guarantee, and splitting `mcp_ro_policy`'s grants across three modules would leave no single auditable answer to "what can the MCP role read". The one-role-per-file naming (`mcp_ro_policy.sql`) replaces the database-named `grants_mcp_ro_policy_db.sql`.
4. `public_hardening.sql` stays inlined rather than split out: `metadata_db` separates it because three roles would each redundantly revoke PUBLIC's CONNECT; `policy_db` has one served role, so the revoke lives in that role's file with a comment explaining the deviation.
5. Comment application must be unconditional on every run (not only at first creation): the live database already carries every description, so convergence is free — re-running a config refreshes comments while `overwrite = false` skips the data loads. This is also why task 8's live verification is cheap.
6. A corpus's `schema_comment` is repeated identically across its configs (20+ files for cms_iom): last-writer-wins makes divergence harmless but sloppy; identical text is grep-checkable. The alternative — a single per-corpus descriptions config — would reinvent the side file this activity removes.
7. `config/test/ingest_test_document.toml` carries no comment keys because it loads into the live `cms_iom` schema; a test-flavored `schema_comment` would overwrite the production schema description on every test run.
8. The `briefs` configs (`config/briefs/`, `generate_embeddings_briefs.toml`, the excel example) get no comment keys: the briefs_db descriptions were retired on 2026-08-16 with the pg_metadata move out of `mcp_deployment`. The knobs are optional, so those configs are unaffected; descriptions can be authored in config if briefs_db is ever re-ingested.
9. Comment text is a SQL literal, not an identifier — `validate_sql_identifier` does not apply. The texts contain `&`, `/`, parentheses, and em-dashes today and could contain single quotes; tasks 3.2 and 6.1 pin the quoting behavior with tests. Implementation route: PostgreSQL rejects server-side bind parameters in utility statements like `COMMENT ON`, but this repo's engines use the psycopg2 driver, which interpolates parameters client-side — so `conn.execute(text("comment on table ... is :c"), {"c": ...})` works and quotes safely (the same mechanism as `apply_ddl.py`'s `%s`). No hand-rolled literal escaping.
10. This activity creates no new data tables; its DB output is catalog metadata (`obj_description` / `shobj_description`). Validation is therefore the task 8.4 catalog query (zero undescribed tables across the three schemas, exact-text match for touched tables) rather than a per-table `data_val_*` script.
11. Task 9.4 applies the rewritten grants live as `policy_db_maintainer` — grants are additive and idempotent, so a re-application against the unchanged privilege model is a no-op that proves the parameterized rewrite renders correctly. Any privilege diff on the spot-check is a blocker.
12. The `qpp_cm` structured-table descriptions carried a verification caveat in `qpp_cm_descriptions.sql:14-16` (verified against columns and sample data; QPP semantics refinable). That caveat travels into the qpp_cm config comments as a TOML comment so it is not lost with the deleted file.
13. Live data is reachable (`.env` holds the Postgres connection; the MCP servers are read-only viewers of the same corpus), so sample runs and live verification are in-plan per the reachability rule; only the full-corpus comment-refresh sweep (8.5) is deferred to manual follow-up.
14. Pre-verified environment state (2026-08-16), which the plan's run and verification steps depend on: (a) this checkout has NO `data/` tree — the 2.0 GB corpus data lives in the pre-split monorepo checkout at `..\rag\data`; config paths are cwd-relative, the Excel leg parses source workbooks directly, and the file leg's parse/clean steps need the parsed/cleaned JSON on disk to skip cleanly, so without task 8.1's copy the runs exit 1 on parse failures even though comment application itself would still execute. (b) The live DB has 49 tables across the three schemas and exactly two undescribed ones — `cms_iom.test_document` and `cms_iom.test_document_content`, with no test embedding table — so task 8.2 closes precisely that gap and 8.4's zero-undescribed target is reachable. (c) A `pg_metadata` reference sweep of both repos found, outside `code/pg_metadata/` itself, only this repo's README + contract (task 11) and `mcp_deployment`'s README + contract (task 12) as non-historical references.
15. (b) The excel template's generic `sheet` comment neutralizes the retired qpp_cm text's one flavored phrase — "the per-measure table it was loaded into" became "the structured table it was loaded into" — so the corpus-neutral template never claims qpp_cm semantics; this is a second (deliberate, verified in 8.4) live-text change beyond decision 2's usc embedding text.
