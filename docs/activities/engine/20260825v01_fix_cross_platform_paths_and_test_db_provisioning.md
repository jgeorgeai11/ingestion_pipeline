## Key Data Decisions and Considerations

1. **Reject the ambiguous form rather than banning absolute paths or accepting them consistently.** Three options existed for `resolve_config_path`. Accepting POSIX-absolute paths everywhere would make `/data/x` resolve to the current drive's root on Windows — a drive-dependent result worse than either alternative. Banning absolute paths outright would enforce the self-contained-instance invariant but removes a real escape hatch (a corpus parked on another volume) that nothing currently needs. Rejecting only the ambiguous form — rooted under one platform's rules but not the host's — eliminates the silent divergence, changes no currently working config, and keeps the escape hatch. If the stronger invariant is wanted later, it belongs in the documented instance contract first and is then a one-line tightening at the same code point.
2. **The predicate belongs in `ingpipe_lib`, not `ingpipe_acquisition`.** Engine packages may never import each other, so once `ingpipe_lib.paths` needs the same check, a copy under `ingpipe_acquisition` is structurally unreachable from the library. `ingpipe_lib` already owns path anchoring and validators, making `paths.py` the natural home next to `resolve_config_path`.
3. **The predicate tests for a drive or root, not for absoluteness, and is named accordingly.** The first draft of this activity specified `is_absolute_path(raw)` as `PurePosixPath(raw).is_absolute() or PureWindowsPath(raw).is_absolute()`. That is wrong for three forms, verified 2026-08-26: `C:data` and `D:data` (drive-relative) and `\etc\passwd` (drive-less root) are absolute under neither rule set, yet `PureWindowsPath('C:/root/out') / 'D:data'` is `D:data` and `PureWindowsPath('C:/root/out') / '/etc/passwd'` is `C:\etc\passwd` — both outside the root. What the guards actually need to know is "is this safe to join under a root?", so the predicate tests for a drive or a root under either rule set, and is named `is_rooted_path` because "absolute" is precisely the word that produced the original defect. This one correction propagates into the predicate spec (task 2), its adoption, test cases, and conventions guard (tasks 3–6), and the house rule written into MAINTAINING §2 (subtask 14.1), which would otherwise enshrine the incomplete rule.
4. **`resolve_config_path` is the right choke point.** It is the single function every config-authored filesystem path passes through — 10 call sites across seven modules in all four stage packages (`runner.py`, `data_val_downloads.py`, `ingest.py`, `data_val_cleaned_json.py`, `quality_report.py`, `ingest_excel.py`, `data_val_excel_inputs.py`), re-counted 2026-08-26; an earlier draft said seven, which was the module count. Fixing it once covers acquisition, file ingestion, excel ingestion, and quality reporting; fixing it in each package's `validate_config` would be four implementations free to drift. This sits slightly against "producers own config validation," but that rule governs per-package config shape, and this function already raises a config-shaped error (`InstanceRootNotFoundError`).
5. **The `discover.py` gap was wider than the `runner.py` one, and none of the three was a security hole.** `runner.py` and `extract.py` both have a `.resolve()`-comparison backstop behind the rooted check, and `discover.py` feeds `runner`, so even the drive-relative escape in decision 3 is caught before a byte is written. What the defects cost is a wrong and late error message, plus one discovery site that on Windows validated nothing. The three sites should not be described as equivalent, and none should be described as an exploit.
6. **The stored manifest was never affected.** `manifest.py` already writes `destination.as_posix()` and each artifact's `path.as_posix()`, so the portability guarantee in MAINTAINING.packages.md §5 — that paths are stored relative so an instance directory can move — held throughout. Only rendered validator messages varied by host, which is why task 7 is cosmetic and carries no data migration.
7. **The `quality_report.py` encoding is latent, not live.** `json.dumps` defaults to `ensure_ascii=True`, so today's output is pure ASCII and no locale can corrupt it. The fix is worth making because it was the only production write without an explicit encoding, and anyone adding `ensure_ascii=False` or a non-ASCII key would get mojibake or a `UnicodeEncodeError` on a non-UTF-8 locale. The single test-side instance (task 12) is the same defect class; an earlier draft counted 76 by single-line grep, corrected in subtask 12.1 by running the rule itself.

An honest skip with a stated reason, plus real coverage on macOS, is the better trade.
9. **Newline translation was examined and deliberately left alone.** `manifest.py:274`, `file_parser.py:365`, and `ingest.py:375` write text with the default `newline=None`, so JSON files get CRLF on Windows and LF on macOS. This was checked against every hash in the engine and affects none of them: the excel hash covers in-memory `row_text` joined and UTF-8 encoded, and the document hash covers the original binary source. The artifacts differ byte-wise across platforms but parse identically, so changing it would be churn.
10. **The unifying defect is host-dependence, not "Windows bugs".** Every item here is a value whose meaning is fixed by contract being judged, rendered, or provisioned by asking the host: predicates that ask the host (`Path.is_absolute()`, POSIX mode bits), rendering that leaks the host into a compared or stored string (separators, encoding, newlines, local-time timestamps), and provisioning that assumed one cluster's privilege model. Naming the class is what produced tasks 10, 12, 15.4, and 16, which no failing test pointed at. The class was invisible until the second platform was first exercised, and §2 records that there is no CI — so "green suite" was never evidence for it.
