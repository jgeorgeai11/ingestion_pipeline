## Key Data Decisions and Considerations

1. **Only the examples are guarded; the real configs are deliberately left alone.** A real config is parsed and run through its producer's `validate_config` at the start of every run, by validators that carry deliberately specific messages and are already thoroughly tested against synthetic inputs. A malformed one fails in seconds, naming the line or the key. Testing the ~30 real configs would add a config-to-validator routing table to maintain in exchange for catching what already fails loudly and immediately. The example is the opposite case: nothing ever executes it, so drift is silent, permanent, and lands on whoever copies it. The rule applied here is to test what nothing else exercises.
2. **The helper belongs in `ingpipe_lib`.** Engine packages may never import each other, so a single parametrised test over all four validators could not live in any one package's `tests/` — that package's suite would then fail when installed alone in a scratch environment, which is the isolated-install property MAINTAINING.packages.md §1 protects. Every member may depend on `ingpipe_lib`, and `ingpipe_lib.testing` already hosts the shared `ephemeral_schema` fixture, so it is the one placement that respects the rule. This is the same reasoning that put `is_rooted_path` there in the portability activity.
3. **`importlib.resources`, not a relative path — and precisely what that buys.** In the editable workspace, `files("<package>")` resolves to the SOURCE tree (verified 2026-08-26: `files('ingpipe_acquisition')` returns `packages/ingpipe_acquisition/src/ingpipe_acquisition`), so the routine suite run proves the file exists at its canonical import location — it can NOT detect a wheel that omits the file. The mechanism becomes load-bearing in MAINTAINING.packages.md §1's honest shipping check — installing the package alone from its wheel in a scratch environment and running its suite there. In that environment `files()` resolves into site-packages and genuinely proves the file shipped, while a test-file-relative read would still pass wrongly, because the repo checkout (where the tests live) is present either way. The resource read is therefore the only implementation under which the isolated-install check exercises shipping at all.
4. **The 2026-08-25 `cms_iom` defect is an operational gap, not a coverage gap, and is out of scope.** Two configured filenames pointed at files not on disk, so two documents were skipped on every run. `data-val-loaded-documents` exists to catch exactly that and checks the real filesystem; it simply was not run. Reimplementing a partial, corpus-dependent version of it inside pytest — which would have to skip whenever the gitignored 2 GB corpus is absent — would be the wrong answer to a discipline problem, and would add a second class of silent skip to a suite MAINTAINING.packages.md §2 already warns about on that count.
5. **If an example fails, the example is presumed wrong.** The validator is the contract's implementation and is exercised by every run and by its own tests; the example is unexecuted prose. Fixing the validator to match a stale example would break real configs. The exception is a validator that is itself wrong — in which case the fix is a separate change with its own reasoning, not something folded into a documentation repair.
6. **The drift question was answered before implementation: all four examples currently pass.** An earlier draft expected task 3 to surface failures, since no example had ever been checked. On 2026-08-26 every shipped example was parsed and run through its own package's `validate_config`, and all four validate cleanly — so the activity buys the permanent guard and surfaces nothing today. Subtask 3.5 stays as contingency only for drift arising between that verification and implementation.
7. **No new dependencies, and specifically not a schema library.** `jsonschema` or a `pydantic` model would give declarative validation, but either means a second definition of the contract sitting alongside `validate_config` and free to disagree with it — the same drift problem one level up. The repo's validators are hand-rolled for message quality (the `overwrite = "false"` rejection is documented behaviour with a recorded rationale), and a rewrite would change both message text and exception type.
8. **This activity writes no data file or table, so it carries no data-validation tasks.** Everything it produces is test code, one library function, and one activated example section. The outputs verified are the suite and static analysis, in task 5, plus the wheel-listing check subtask 3.3 triggers by editing package data.
9. **`ingpipe_lib.testing` is itself currently untested**, which is why task 2 creates a test file rather than extending one. Worth noting that the `ephemeral_schema` fixture every DB-backed test in the workspace depends on has no direct coverage of its own; that is not addressed here, but task 2 establishes the file it would go in.
10. **Task 3 deliberately groups four test files into one task.** Each receives the identical one-test addition for the identical reason — the repeated-change case — and every affected file is named in the task header. Splitting them would fan one rationale across four workers that must agree on the helper's name and calling convention.
11. **The acquisition example's `content_checks` block is activated rather than left as comments.** A commented-out block is contract documentation the guard cannot reach: it can drift from `validate_content_checks` exactly the way an unchecked example drifts from `validate_config`, which is this activity's defining defect. Activating a minimal real table makes the shipped example exercise both of the package's validators. The alternative — dropping the check and leaving the comments — was rejected because it preserves precisely the silent-drift channel the activity exists to close.
12. **The root pyproject's mypy override list no longer matches its own comment, and this activity only avoids widening the gap.** The comment says every test module is enumerated, but the five archive_db test modules added 2026-08-26 are absent (mypy is nonetheless clean, because the disabled error codes exist for fixture-heavy patterns those modules avoid). Subtask 2.6 enrols this activity's own new module plus `test_conventions` on behalf of the portability activity — that plan was already frozen and mid-implementation on the other machine when the enrolment item was identified, so amending it was no longer an option and this activity is the next plan through the file. Back-filling the five archive_db modules, or revising the comment, belongs to the archive_db workstream.
