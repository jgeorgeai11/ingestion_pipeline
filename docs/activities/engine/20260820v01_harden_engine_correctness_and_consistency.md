## Key Data Decisions and Considerations

1. Phase 1 now holds the three silent-data-loss guards, and the reason they may precede the test infrastructure is what kind of fixes they are: input rejections — a `ValueError` on a non-boolean `overwrite`, a warn-and-skip in the chunker, a range check on `header_row` — verified by pure unit tests that need no database. The danger they remove is live today, so they should not wait behind infrastructure they do not use. The instrument argument still governs everything SQL-shaped: `file_ingestion` and `embedding_generation` assert their SQL by substring-matching statements captured from a `MagicMock`, so a syntax error, wrong column name, broken `ltree` cast, or absent rollback passes at 99% coverage — which is why Phase 2 builds the real-database fixtures before any phase that touches the engine factory, transactions, DDL, or validator SQL. This ordering was originally an out-of-band agreement recorded in the workspace activity's decision 14; it is now the written order so the plan needs no external context.
2. The engine must verify extensions, never create them. Today all three pipelines issue `create extension if not exists` as part of their DDL, which asks every ingest run to hold a privilege it should not have: installing an extension is a one-time provisioning act on the database, not a per-run step. The current arrangement only appears to work because `policy_db_maintainer` owns its database and `ltree` happens to be a trusted extension. It breaks the moment either assumption fails — verified 2026-08-20 on `ingestion_test`, where the owning role created `ltree` successfully but `vector` failed with `permission denied to create extension "vector"`, because pgvector is not trusted. A checked precondition also fails better: `require_extensions` reports the missing extension and how to install it, where the current path surfaces an opaque privilege error from the middle of a DDL transaction. Creation moves to where provisioning already lives — the superuser-run `create_ingestion_test_db.sql` for the test database, and a documented one-time step for each instance database.
3. The shared engine factory adopts the behavior of `excel_ingestion/_utils.py:56` and `ingest.py:67`, which are mutually identical and already correct: `URL.create` (which percent-encodes credentials), an `int()` port guard, and a logged `ValueError`. The other three copies each drop something — `generate_embeddings` and `data_val_embeddings` omit the ERROR log, `generate_embeddings` raises `ConfigurationError` instead of `ValueError`, and `data_val_loaded_documents` uses an f-string URL and omits the port guard. Consolidation is therefore a bug fix, not only a tidy-up: it deletes the f-string defect rather than patching it in place.
4. Tasks 1, 3, 4, 11, 14, 15, 16, 19, 20, 21, and 26 each touch more than one code file, deviating from the one-code-file-per-task rule (precedent: repo-split activity decision 7, reorganization activity decision 11). Each is one change repeated across named files — removing the same `create extension` line, swapping a factory import, adopting a shared preamble, adding the same type guard, rejecting the same out-of-range value, adding the same CHECK constraint to two sibling schemas — so per-file tasks would obscure rather than clarify. Every affected file is named in a subtask.
5. This activity creates no new data tables, so no new per-table `data_val_*` script is written (precedent: repo-split decision 10, reorganization decision 9). It does change the *contents* of one existing output — the four `*_embedding` tables (decision 20) — and that is validated by `data_val_embeddings.py`, which already owns it. That validation is only trustworthy once Phase 5 gives those scripts real tests, which is why the plan tests the validators before relying on them; task 28.5 then runs them end to end. The remaining outputs under test are behavioral: the suite passing from any CWD and the coverage floor in task 28.2.
6. The chunker's no-words case is handled by warn-and-skip rather than by emitting the raw text as a chunk. A section that exceeds the token budget yet contains no whitespace-delimited words is pure whitespace, so embedding it would spend a model call and a stored row on content with no retrievable meaning. The tradeoff accepted: because the resume path is a PK-only left-anti-join, a skipped row is re-selected on every future run. That is unchanged from today's behavior — what changes is that it is now logged and counted rather than silent, which is the actual defect.
7. Rejecting out-of-range row indices (task 3) is a hard error rather than a clamp. `header_row = 0` is unambiguously a mistake — TOML row numbers are 1-based everywhere else in these configs — and silently clamping to row 1 would ingest a plausible-looking but wrong result, which is the failure mode being fixed.
8. Resolving merged cells (task 16.1) may require abandoning `read_only=True` in openpyxl, which trades memory for correctness on large workbooks. Prefer reading the merged-range metadata separately and keeping the read-only data pass if that proves workable; if not, accept the memory cost and record the measured difference on the largest instance workbook, since silently losing every continuation value of a merged category column is the worse outcome.
9. Where the two row-text builders disagree on NULL (task 17.1), the Excel behavior wins: `build_row_text` renders `col: ` for a NULL value and its comment explains why — a stable field layout across rows means the embedding model sees a consistent schema. `_build_embed_text` omitting the line entirely makes the layout vary per row, which is the behavior worth changing.
10. Task 18.1's delete-then-insert window may not be fully closable while streaming: the delete must precede the stream, and holding one transaction across an entire corpus-sized run would bloat the transaction and hold locks for its duration. If bringing the delete into the first batch's transaction proves impractical, documenting the window explicitly (and noting that a rerun re-detects the missing rows) is an acceptable outcome — but it must be a recorded decision, not the current silence.
11. Task 14.3 changes a config schema, which makes it the one task here with a blast radius outside the engine packages. Reading the nested `[load]` form as a deprecated fallback with a warning means existing configs — including any on the machine running `archive_db_rag`, which this repo cannot see — keep working rather than failing at the next run.
12. Phase 6 is scoped to adopting the tools and fixing what they surface in engine code, not to an unbounded cleanup. If ruff or mypy surfaces a large backlog of pre-existing findings, fix the correctness-relevant ones, record the rest behind explicit rule exclusions with a comment, and open a follow-up activity — a lint backlog must not block the correctness work in Phases 1, 4, and 5.
13. Data reachability: the local PostgreSQL server, the `ingestion_test` database, and superuser access are all available on this machine, so every test and smoke run in this plan executes here rather than being documented for manual execution. One environmental gotcha to know before diagnosing import failures as code problems: Python 3.14 skips *hidden* `.pth` files, silently unloading every editable install. On macOS the hidden state is a file flag (`chflags nohidden .venv/lib/python3.14/site-packages/*.pth` fixes it; recurred twice on 2026-08-20/21, recorded in commit `83503c2`); on Windows the analog is the hidden attribute (`attrib -h` on the same files). The `ltree` extension was created in `ingestion_test` on 2026-08-20 while verifying decision 2; task 4.5 makes that state reproducible from the script.

15. The full corpus is being rebuilt after this activity, which removes backward-compatibility as a constraint on every task here. Two consequences, both deliberate. First, changes to embedded content need no reconciliation: altering how embed text is built (task 17) would ordinarily be a re-embed event — same model, different input text, different vectors for an unchanged source row — but a rebuild regenerates every vector from the new layout, so each such choice is made on its merits rather than hedged against what is stored. Second, and more valuable, DDL additions actually take effect: both schema templates are `create table if not exists`, so anything added after first deployment never reaches an existing environment and needs a manual `ALTER TABLE` (the migration caveat at `schema.sql:11-17` and `excel_schema.sql:15-18`). Several DDL review findings were deferred on exactly that basis, so task 21 re-decides them while the window is open rather than deferring them into a state that is again unreachable once the rebuilt corpus is in place. The rebuild is a window, not a standing condition — after it closes, the migration caveat applies again.

Three tasks come close to it without crossing: task 4 stops *creating* the `vector` extension but still requires it, so the `vector`-typed column the server discovers via `udt_name = 'vector'` is unaffected; task 18.3 changes an index name, and indexes are not part of the contract; task 17 changes chunk text content, not table shape. If any of these turns out to alter the shape, the change must land in `mcp_deployment`'s copy of the contract in the same breath.

Running the validator against a schema being actively loaded produces arbitrary results with no warning. This activity does not add enforcement, because the fix (a repeatable-read transaction, or an advisory lock shared with the loader) is a design change rather than a defect repair; task 22 will pin the documented behavior as-is, and enforcement is a follow-up.

21. Package boundaries change what "adding a dependency" means, and the shared venv hides mistakes. Each package now declares its own dependencies, so when this activity moves code into `ingestion-lib` (the engine factory, `require_extensions`), the lib's `pyproject.toml` must gain the imports' dependencies — today it declares only `python-dotenv` and `python-json-logger`. The trap is that nothing fails locally if the declaration is forgotten: `uv sync` installs every member into one venv, so sqlalchemy is importable from anywhere regardless of who declared it. The only honest check is an isolated install (task 9.5), the same instrument the workspace conversion used to prove package independence. The same reasoning bans new cross-imports between engine packages (grep in task 28.3): the local venv would let them work while breaking every isolated consumer. Relatedly, instances should treat engine internals (each package's `_utils`) as private — their supported surface is the console scripts plus `ingestion_lib` — recorded here as a convention since nothing enforces it yet.
