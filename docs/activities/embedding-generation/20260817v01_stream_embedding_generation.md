## Implementation Plan

1. [completed] Stream source rows and batch the inserts - `code/embedding_generation/generate_embeddings.py`
   - 1.1. Replace the `fetchall()` + full-table `row_groups` materialization (currently `generate_embeddings.py:582, 598-655`) with a streamed read over the existing left-anti-join SELECT: `conn.execution_options(yield_per=...)` / `stream_results` (a psycopg2 server-side cursor), keeping the existing `order by` on the source PK
   - 1.2. Build each row's chunks as its row is consumed and accumulate into the current batch; flush when the batch reaches `batch_size` chunks. A row's chunks never split across flushes (a single row larger than `batch_size` still becomes its own larger, atomic batch), preserving the whole-row atomicity guarantee the left-anti-join re-detection depends on
   - 1.3. `_flush_batch` executes the INSERT once with the full parameter list (SQLAlchemy executemany) inside the same per-batch transaction, replacing the one-`conn.execute`-per-chunk loop (currently `generate_embeddings.py:676-686`)
   - 1.4. Keep an up-front `select count(*)` over the same filtered anti-join so the "Found N rows needing embeddings" log line, the "No rows need embeddings, skipping" early return, and the `X/total` progress logging keep their current semantics (see decision 6)
   - 1.5. Unchanged behavior to preserve: the overwrite DELETE, the `COMMENT ON` application, the header-budget chunking, the return value (total inserted), and every log message's information content

2. [completed] Update the test harness and pin the new loop's contracts - `code/embedding_generation/unit_tests/test_generate_embeddings.py`
   - 2.1. Rework `_setup_generate_embeddings_mocks` for the streamed read (the mocked result iterates rather than `fetchall()`) and for executemany capture: record per-statement, filtered on the statement text, so the overwrite DELETE's params are no longer collected into `insert_calls` (this also completes `cr_20260816v01_test_generate_embeddings.md` finding 4.1 in its new shape)
   - 2.2. Assert: the INSERT is called once per batch with a `list` of param dicts whose length equals the batch's chunk count; a multi-row batch keeps each row's chunks in a single flush; a row exceeding `batch_size` flushes alone; and flushing begins before the source iterator is exhausted (streaming, not materialize-then-flush)
   - 2.3. Keep every existing behavioral assertion passing unchanged (chunk_text content, header prepending, overwrite delete-then-regenerate, no-rows early return); run `uv run pytest code/embedding_generation/unit_tests`

3. [completed] Live equivalence verification on a bounded subset - `code/embedding_generation/generate_embeddings.py`, `code/embedding_generation/data_validation/data_val_embeddings.py`
   - 3.1. Before running the re-embed in 3.2 (the live table still holds the pre-refactor output, so this can run at any point before that write), snapshot the baseline for one small slice to a scratch JSON file (session scratch directory, not committed): row/chunk counts and a few sampled `chunk_text` + `word_count` values for a narrow `source_filter` pattern (e.g. one qpp_cm workbook's `collection_path` prefix on `qpp_cm.sheet_content_embedding`)

   - 3.3. Run the existing output validator (`uv run code/embedding_generation/data_validation/data_val_embeddings.py --config` its qpp_cm config) and confirm it passes

## Key Data Decisions and Considerations

1. Origin: `docs/code_review/embedding_generation/cr_20260816v01_generate_embeddings.md` findings 3.1 (whole-result materialization; assessed as a minor, re-tagged suggestion in that review on deferral here per the severity/resolution convention) and 6.2 (per-chunk INSERT round trips), deferred there to this activity. They are bundled because both restructure the same loop and invalidate the same test-harness capture; done separately, the loop and its tests would be rewritten twice.
2. Why not part of the 20260816v01 fix round: this is the one change that alters the shape of proven-live code (the corpus was fully embedded and verified through this loop on 2026-08-16). It gets its own plan, its own assertions, and its own live equivalence run rather than riding among ~40 mechanical fixes.
3. The memory target is peak proportional to `batch_size` chunks (plus one in-flight row and the loaded model), not to table size. The case that motivates it is the full re-embed — the contract's model-change event (`docs/contracts/corpus-schema-contract.md` §4) — which is exactly when the un-embedded set equals the whole corpus.
4. Whole-row atomicity is the invariant that must survive: a row's chunks commit together, so a mid-run failure leaves only whole rows un-embedded, which the PK left-anti-join re-detects on rerun. Streaming preserves this as long as flush boundaries fall between rows (task 1.2); the executemany call sits inside the same per-batch transaction, so the boundary is unchanged.
5. Streaming mechanism: a single server-side cursor (`stream_results`/`yield_per`) over the already-ordered SELECT, not keyset pagination — one cursor is simpler, the result set is a read-only snapshot, and the existing `order by` guarantees deterministic consumption. The psycopg2 driver supports named cursors; this is the same driver dependency the module already documents for its `COMMENT ON` binding.
6. The up-front `count(*)` (task 1.4) is a deliberate second query: it preserves the operator-facing "Found N rows" / "No rows, skipping" semantics and the existing tests' expectations, and its cost is negligible next to embedding compute. The count and the stream could disagree if rows were inserted mid-run; the pipeline is single-writer, and the count is used only for logging, so no correctness depends on it.
7. Sequencing: implement AFTER the cr_20260816v01 review fixes land in `generate_embeddings.py` and its test file — those touch the same files (docstrings, type hints, `tables` shape guard, harness annotations), and this activity assumes their state as its baseline.
8. Validation is the task 3 equivalence check rather than a new `data_val_*` script: the activity changes no schema and no output contract, so "same inputs produce identical chunk rows" plus the existing `data_val_embeddings.py` is the right gate. Embedding vectors are regenerated, not byte-compared — the pinned model makes the text columns the deterministic surface.
9. Live data is reachable (`.env` holds the Postgres connection), so the bounded re-embed and validator runs are in-plan; a full-corpus re-embed is explicitly NOT part of this activity (nothing about the change requires one).
10. Implementation deviation from task 1.4/1.5 (log lines): the per-batch progress denominator could not stay `chunks/total_chunks`, because the total chunk count is unknowable until the stream is drained — the very materialization the activity removes. The count(*) supplies a ROW denominator instead, so the progress line is now `Inserted batch of N embeddings from R rows (rows_done/total_rows rows, chunks_so_far chunks total)`: same per-batch chunk count, same running chunk total, denominator over rows rather than chunks. The `Chunked N rows into M chunks (max_tokens=..., overlap=...)` line keeps its exact information content but now prints AFTER the loop (it is a result, not a plan) rather than before the first insert. "Found N rows needing embeddings", "No rows need embeddings, skipping", and the final "Embedding generation complete: N embeddings inserted" are unchanged.
11. Streaming/count wiring as built: `count_sql` and `select_sql` are composed from one shared `anti_join_source` FROM/JOIN/WHERE fragment, so the two queries cannot drift apart; `select_sql`'s text is byte-identical to the pre-refactor version. The read uses `conn.execution_options(yield_per=max(batch_size, 1))` (verified on SQLAlchemy 2.0.46 to return the same `Connection`, which is also how the test harness mocks it); the `max(..., 1)` floor keeps a misconfigured `batch_size = 0` from reaching `yield_per`. The final partial batch flushes after the `with engine.connect()` block, so the server-side cursor is released before the last write.
12. Task 3 results (2026-08-17): slice `qpp_cm.sheet_content_embedding` where `collection_path::text like '2025_12_py2025_codes_list_cataract1.%'` — the smallest qpp_cm workbook, 9 sheets / 2,207 source rows / 2,207 chunks. Baseline and post-re-embed snapshots (counts, `sum(word_count)` = 226,765, 10 sampled `chunk_text`/`word_count` values, and an md5 over EVERY chunk's ordered `chunk_text`/`word_count` — `dd7d84bf01505cd4a9070322936575df`) are identical; all 2,207 rows carry a non-null 384-dim vector and the table's total row count is unchanged at 1,340,050 (the overwrite DELETE + regenerate netted zero). The run logged `Overwrite: deleted 2207` → `Found 2207 rows needing embeddings` → 35 batch flushes → `2207 embeddings inserted`. `data_val_embeddings.py --config .../generate_embeddings_qpp_cm.toml` then passed over both qpp_cm tables (exit 0, no WARNING/ERROR: source rows embedded 1340010/1340010 and 3096/3096, vectors non-null at 384, chunk_tsv + GIN present, truncation gate clear). The temporary config was deleted; the snapshot JSONs live in the session scratch directory only.
