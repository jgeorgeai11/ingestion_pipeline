All data values bound as parameters; identifiers validated + quoted.

## Key Data Decisions and Considerations

1. Hybrid storage is the standard for tabular RAG: a text/embedding leg for semantic retrieval and a structured leg for SQL/text-to-SQL. Flattening tables to a single embedding loses row/column structure ("vector dilution") and embeds numbers/codes poorly, so structured tables are kept for precise/relational queries; text embeddings are kept for semantic search. This module makes `excel_content` (embedding leg) UNIVERSAL and structured tables an additive per-sheet opt-in.
2. (Decision 6) Routing: every sheet is ALWAYS written to `excel`/`excel_content` (no `embed` flag — it is implicit). A sheet that names a `table` is ALSO written to that structured table. The only per-sheet routing input is the optional `table` name. A structured sheet's data therefore lives in both places (intentional redundancy = the hybrid).
3. (Decision 1) Structured-table identity is synthetic: PK `(source_file, sheet_name, row_number)`, `row_number` 1-based positional within the sheet. No config-supplied `pk`, no parent FK. Positional `row_number` is a within-snapshot ordinal (not a stable business key) — acceptable because overwrite replaces a source's entire contribution; duplicate source rows are preserved faithfully.
4. (Decision 2) All structured data columns are `text` (nullable, empty -> NULL). This is the enabler for safe `ALTER ADD COLUMN` + cross-source append (no type conflict, leading zeros/codes preserved). Numeric/date analytics, if ever needed, is a downstream cast in a view — not the ingester's job.
5. (Decision 3) Overwrite is a top-level flag with per-`(source_file, sheet_name)` effect on BOTH legs: `overwrite=true` deletes that source's rows then re-inserts (never DROP TABLE — shared tables); `overwrite=false` skips a source already present (idempotent; fixes the current consolidated dup-key rough edge). Columns evolve additively on every load regardless of overwrite. One transaction per sheet per leg.
6. (Decision 4) Compatibility guard on structured append: refuse only when BOTH `r_in=|∩|/|incoming|` and `r_ex=|∩|/|existing|` (over the `col_*` data-column sets, EXCLUDING the four identity columns) are below `min_column_overlap` (top-level default 0.5) — this allows legitimate superset/subset schema evolution while catching a wrong-table-name clash; on the allowed path, WARN-log every column added/missing so schema drift is visible, never silent. The guard is a safety net for clear clashes, not a semantic-collision guarantee (name-based mapping relies on sane, distinct headers/table names).
7. (Decision 5) Column names: snake_case then `col_` prefix-all, so every data column is an unquoted-safe identifier regardless of reserved words (`window` -> `col_window`) or leading digits (`2021 Q1` -> `col_2021_q1`). This needs no `pg_get_keywords` lookup and no per-name special-casing, keeps the AGENT querying the structured tables (via the MCP `run_sql`) from ever needing to quote identifiers, and cleanly separates data columns (`col_*`) from the unprefixed identity columns. Identifiers are also double-quoted in generated SQL as internal hygiene. `excel_content` still uses ORIGINAL headers in `row_text` (faithfulness for embedding is untouched).
8. Build by evolving `code/excel_ingestion/` (already has both legs) and retiring `code/excel_ingestion_qpp_cm/`. Sheets are declared EXPLICITLY per workbook (one mechanism — no auto-discover), and the parser does only explicit-row-bound extraction (`header_row`/`data_start_row`/`data_end_row`) — there is NO header-anchor/stop-marker/skip-marker/excluded-sheet logic in the ingester. The module ships NO generation/detection code — it is purely a faithful executor of explicit config. qpp_cm's marker-based structure is resolved to explicit row numbers when its config is authored (by inspecting the workbooks, task 13.1) — however that is done is the data owner's concern, outside the module; only the resulting config files are committed. qpp_cm's hand-authored typed DDL becomes auto-create-and-evolve; its ~40 column-name overrides are absorbed by snake_case + `col_` prefixing (the residue — a source typo — is kept faithfully). qpp_cm's `measures` parent table and PDF/`document` linkage are domain modeling that stays OUT of the generic module (downstream concern). Trade-off: explicit `data_end_row` is version-specific, so a reissued workbook with different row counts is picked up by RE-AUTHORING its config (consistent with the regenerate-on-new-data principle), rather than by sentinel detection that would adapt silently.
9. Shared infra (`get_engine`, identifier validation, logging) is currently triplicated across `file_ingestion`, `excel_ingestion`, and `excel_ingestion_qpp_cm` (and `embedding_generation`'s copy carries the `.match` newline bug). This activity sources `validate_sql_identifier` from the canonical `file_ingestion/_utils` (`fullmatch`) and does not add a new copy; broader infra de-duplication across all modules is out of scope here but noted.
10. Resilient accumulate-and-report (per-sheet failures recorded, others continue, non-zero exit if any) matches the `file_ingestion` model for consistency; config-level errors still abort. This makes a one-bad-sheet workbook degrade gracefully rather than aborting the whole config.
11. qpp_cm is a fresh load: the database currently has no `qpp_cm` (or `usc`) schema/tables, so there is NO stale-data migration — the unified structured tables and schema are created fresh on the first qpp_cm run, with no name/structure collision to resolve. (The bespoke `excel_ingestion_qpp_cm` module's data was never loaded into this database.) The work is naturally two phases: Phase 1 = tasks 1-12 (build the unified module + prove it end-to-end on qpp_cm, the only available Excel data — this is where cross-workbook accumulation into shared structured tables gets exercised); Phase 2 = task 13 (retire the old qpp_cm module). The activity is kept as one focused file with this explicit phase boundary so it can be executed/reviewed in chunks.

**Task 12 real-data findings (the proving run surfaced these)**:
1. **Identifier-length bug fixed (engine change).** Two real qpp_cm headers normalize to 64-char `col_*` names (e.g. `col_icd_10_cm_3_digit_diagnosis_code_service_assignment_decision`). Postgres silently truncates identifiers to 63 bytes, so the generated name (full) and the stored name (truncated) diverged: on the later `ALTER ADD COLUMN`, `reconcile_columns` saw the full name as "missing", re-issued the ALTER, and Postgres truncated it back to the existing 63-char name -> DuplicateColumn, rolling back the whole transaction (the `service_assignment` / `service_assignment_ab` tables were lost). Fixed in `_utils.py`: `normalize_column_name` caps at `MAX_IDENTIFIER_LENGTH=63` (strips trailing `_`), and `deduplicate_columns` trims the base before a `_<n>` suffix so the suffixed name also stays <=63. This upholds Decision 5 ("every data column is an unquoted-safe identifier" — a silently-truncated name is not safe). Added 2 regression tests to `test_utils.py` (cap a >63-char header; keep a truncation-collision pair distinct); full suite now 65 passing. Confirmed on the real data: the previously-lost `service_assignment` (75,663 rows / 21 sources) and `service_assignment_ab` (58,954 rows / 11 sources) loaded fully, and `eligible_clinicians`'s long header landed as a single 63-char column.
2. **Compatibility guard fired correctly; resolved by config.** `emergency.xlsx:Triggers` is a structurally different two-code paired-trigger layout (`Code 1`/`Code 2`/`Claim Type(s) Checked`/`Logic Notes`) that shares only `Initial Sort Order` with the standard single-code `Triggers` (4 cols) in the other 22 workbooks (r_in=0.11, r_ex=0.25, both < 0.5). The guard correctly refused to merge it. Resolved by routing it to its own structured table `triggers_emergency` in the config (it is still embedded into `excel_content`) rather than lowering the threshold (0.11 would effectively disable the guard and pollute the shared table with mostly-NULL columns). With this routing the guard never fires. NOTE: this is a HAND override on the committed config — the throwaway generator would re-emit `table = "triggers"` for that sheet, so a future regeneration of `ingest_qpp_cm_2026.toml` must re-apply the `triggers_emergency` rename (and re-confirm any new same-name structural divergences).
