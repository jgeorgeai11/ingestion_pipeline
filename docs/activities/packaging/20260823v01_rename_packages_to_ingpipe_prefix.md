## Key Data Decisions and Considerations

1. The collision is not hypothetical and was caught by a real check. During the acquisition activity's isolated-install verification, `pip` resolved `ingestion-lib` from PyPI and installed a stranger's "Library for data ingestion" (v0.0.7) instead of this repo's shared library, so the package under test failed on missing modules. `acquisition` is likewise taken. Inside the workspace both names resolve correctly because `uv sync` installs the local members, which is exactly why the problem stays invisible until something installs a wheel outside the workspace.
2. All five packages are renamed, not only the two that collide. `file-ingestion`, `excel-ingestion`, and `embedding-generation` are free on PyPI today, but they are equally generic English compounds and equally claimable tomorrow; renaming two and leaving three would also produce a permanently inconsistent set. The marginal cost of the other three is the same mechanical edit, and the prefix note in task 11.2 makes the rule explicit for the next package.
3. Project folders take the underscore form (`packages/ingpipe_lib/`) so the directory and the import name are identical, removing the mental translation the current layout requires (`packages/ingestion-lib/src/ingestion_lib/`). The project folder name is never imported and never appears in metadata, so this is a free choice.
4. Distribution names keep the hyphen (`ingpipe-lib`) because Python packaging normalizes `ingpipe_lib` to exactly that: the two forms are the same name to pip, uv, and PyPI, and the normalized form is what appears in wheel filenames, `uv.lock`, and dependency resolution. Writing the underscore form in `pyproject.toml` would be accepted but would create a cosmetic mismatch with everything the tooling reports.
5. String references that name a module but are not `import` statements are the rename's real hazard, and the reason each package's rename is one task rather than a per-file sweep. Two classes: the 211 `mocker.patch("<module>...")` targets (a rename rewriting only `import`/`from` leaves them patching a nonexistent attribute — a confusing test error, not an import error), and package-named path strings like `resolve_log_dir("file_ingestion/...")` that silently keep writing to the old subdirectory. Both are invisible to a rename that reasons about imports alone. The counts per package (67 file_ingestion, 45 embedding_generation, 28 acquisition, 4 ingestion_lib, 3 excel_ingestion) were measured on 2026-08-23; re-measure by grep before editing rather than trusting them.
6. Console-script command names are unchanged. Only the module path behind each entry point moves, so `ingest-files` stays `ingest-files`. Renaming the commands as well would break every documented invocation in the instance configs' usage headers and both maintaining files for no benefit — the commands are the user interface and carry no collision risk.
7. Task 6.2 must match `acquisition` as a whole word. The instance's own import package is `policy_db_acquisition`, which contains the substring and is deliberately not renamed; a substring replacement would corrupt it into `policy_db_ingpipe_acquisition`. This is the one place in the rename where a naive find-and-replace does active damage rather than merely missing something.
8. The instance is not renamed. `policy-db-instance` and `policy_db_acquisition` are specific enough not to collide, an instance is not a reusable distribution anyone would install from an index, and leaving them alone keeps the rename's blast radius to the engine. When `archive_db` joins as a second instance it follows the same convention.
9. `mcp_ro_policy.sql` remains superuser-only, which the previous activity established: revoking `EXECUTE` on `pg_catalog` functions fails for the database owner with `permission denied for function`. Phase 3 adds five more such revokes, so it deepens that dependency rather than changing it. This is an operational change already reflected in the maintaining docs — the grants step is a superuser task, not a maintainer one.
10. No change is made to `policy_db`. Phase 3 edits the script and proves it against a scratch pair that is then dropped; applying it to the real database is a manual step belonging to the rebuild, like the rest of the grants work. This activity performs no data operation of any kind — no downloads beyond the dry runs, no ingest, no re-embed, no schema drops.
11. The `docs/activities/` and `docs/code_review/` trees keep the old names. Those files record what a reviewer or planner saw at a point in time; rewriting them to match the present would falsify that record, and the code-review tree's paths are deliberately a mirror of where code was when reviewed. Only the three current-truth documents (`README.md` and the two maintaining files) are updated.
12. This activity creates no new data tables or output files, so no per-output validation task is written. What is under test is behavioral and unusually well-suited to proving a rename correct: the suite passing at an unchanged count, static analysis clean, the grep checks for surviving old names, the wheel contents, the isolated install that previously failed, every console script's `--help` from outside the repo, and the two dry runs.
13. Tasks 2, 3, 4, 5, 6, 7, 8, and 11 each touch many files, grouped because each is one mechanical substitution repeated across named files — the same import name rewritten, the same dependency name replaced, the same entry-point path updated. Splitting per file would obscure that each is a single decision applied throughout, and would make the suite-green checkpoint between packages impossible to state.
14. The rename is sequenced library-first because every other package depends on it: renaming `ingpipe_lib` and repointing its consumers (Phase 1) leaves the tree green before the four pipeline packages move independently of each other (Phase 2). Each package's rename ends with a passing suite, so a failure is attributable to the package that just moved rather than to an accumulated batch.
15. Provenance: the collision was surfaced by the acquisition activity's task 26.4 and recorded there as needing a human decision; the residual large-object functions were surfaced by its task 21 and recorded in `mcp_ro_policy.sql` beside the revokes. Both are closed here. All five residual functions plus the four already revoked were confirmed executable by `mcp_ro_policy` against the live `policy_db` on 2026-08-23, which is the pre-hardening baseline since the hardened script has not been applied there.

### Implementation notes (2026-08-24)

16. **Baseline, and a broken `.venv` found first.** The pre-rename baseline is **936 tests passed**, `ruff check packages instances` clean, `mypy packages instances` clean (78 source files); every later checkpoint is compared against those numbers. The first `pytest` run failed to collect 16 modules with `ModuleNotFoundError: No module named 'ingestion_lib'`: the existing `.venv` had been corrupted out of band (a duplicated `lib 2/` directory and a `_editable_impl_policy_db_instance 2.pth`, the signature of a Finder/sync copy). `uv sync` reported "Audited 133 packages" and did not repair it. Deleting `.venv` and re-syncing fixed it. Unrelated to the rename, but worth recording: a stale editable install makes a rename look like it broke something it did not.
17. **Task 2.2 was necessarily done inside task 1, not after it.** Task 1.4 requires `uv sync` and the library's suite to pass "before any consumer is touched", but `uv sync` cannot resolve the workspace while five `pyproject.toml` files still require the now-nonexistent `ingestion-lib`. The dependency-name repoint (2.2, plus the root's matching entry from 8.1) was therefore applied immediately after 1.1–1.3, and only then were the library's 104 tests run. No consumer *import* was touched before that point, which is the guarantee 1.4 exists to give.
18. **The plan named the wrong logging function, and there were far more package-named path strings than 3.4 expected.** `setup_module_logging` does not exist; the real entry-point helper is `ingpipe_lib.cli.setup_entry_logging`, and the log subdirectory also arrives via `LOG_SUBDIR` module constants (`runner.py`, `data_val_downloads.py`) and via `resolve_log_dir` directly. Fifteen call sites carried a package-named subdir, not the "only current instance" 3.4 predicted: every entry point and every `data_validation` module in all four pipeline packages, plus four test modules using `resolve_log_dir("<pkg>/unit_tests")`. All were rewritten. `runner.py`'s own comment states the intent the plan relied on — the log subdirectory "mirror[s] the module path the way the rest of the workspace does" — so a rename that moves the module must move the subdirectory.
19. **The instance's per-package `config/` and `logs/` subdirectories were renamed too — a decision 7.2 left open.** `MAINTAINING.packages.md` documents logs as landing under `<instance>/logs/<package>/` and `MAINTAINING.instance.policy_db.md` describes `config/` as "per-package TOML configs", so both are package-named by rule, not coincidence. Renaming the log-subdir strings (18) while leaving `config/file_ingestion/` would have split one convention in two. The four `instances/policy_db/config/<package>/` directories were `git mv`d and every `--config` path in the maintaining files, the packages' docstrings, and each config's own usage header was updated. This does NOT contradict decision 8: the distribution name `policy-db-instance` and the import package `policy_db_acquisition` are untouched, which is what 7.2 actually names. The old `instances/policy_db/logs/{acquisition,file_ingestion,embedding_generation}/` directories are gitignored run artifacts and were deliberately left on disk rather than deleted; new runs write under the `ingpipe_` names (confirmed by the task 12.7 dry runs).
20. **Three `acquisition` occurrences are deliberately NOT renamed**, beyond the `policy_db_acquisition` guard decision 7 anticipated. `acquisition` is an ordinary English word and appears as prose throughout ("an acquisition run", "the acquisition engine", "Document acquisition, ingestion, and embedding generation"); a whole-word replace would have corrupted all of it, so the rename was driven by classified contexts (import/dotted-module, `mocker.patch` target, entry point, dependency name, `packages/`/`src/`/`config/` path, `LOG_SUBDIR`) enumerated from a dry run and reviewed before writing. Kept as-is: (a) English prose; (b) `MANIFEST_FILENAME = ".acquisition_manifest.json"` — an on-disk artifact name, and renaming it would orphan every manifest already written beside a corpus, silently making the next run re-download everything; (c) the function `run_acquisition`, which names an act, not a module.
21. **Two test modules were renamed to keep matching their package**, and the root `pyproject.toml` mypy module list with them: `test_file_ingestion_utils.py` → `test_ingpipe_file_ingestion_utils.py` and `test_excel_ingestion_utils.py` → `test_ingpipe_excel_ingestion_utils.py`. That list is enumerated (mypy's per-module patterns cannot express `test_*`), so a renamed test file that is not also renamed in the list silently loses its exclusions; the two entries were moved to keep the list alphabetical.
22. **8.4 verified, with one correction:** `[tool.mypy] files = ["packages", "instances"]` and `[tool.ruff] include = ["packages/**/*.py", "instances/**/*.py"]` are directory/glob-based and survive the rename. There is no `[tool.coverage]` section anywhere in the repo — coverage runs through `pytest-cov` flags, so there is no include list to update. The `[tool.ruff.lint.per-file-ignores]` key (8.2) needed BOTH halves rewritten (`packages/embedding-generation/` → `packages/ingpipe_embedding_generation/` and the inner module), and now points at a file that exists.
23. **The rename lengthened lines, and that was cleaned up rather than left.** `ingpipe_` adds 8 characters to every occurrence, which pushed ~25 Python lines past the workspace's 100-character limit — invisible to CI, because ruff's `select` does not include E501. Every line the rename pushed over was reflowed (`mocker.patch` calls split across lines, long asserts parenthesized, comments and docstrings rewrapped); the workspace went from 50 over-long Python lines before the rename to 43 after. The instance config files' `# Usage:` headers were already well over 100 before the rename and are not Python, so they were left alone.
24. **A double-prefix bug was introduced and caught by an explicit check.** Applying `packages/<old-hyphen>` → `packages/ingpipe_<new>` before `<old_underscore>` → `ingpipe_<new>` made the second rule re-match inside the first rule's output, producing `packages/ingpipe_ingpipe_embedding_generation` in the root `pyproject.toml` (including the ruff `per-file-ignores` key) and three `README.md` rows. Nothing failed — the suite stayed green, because a comment and a lint-exemption key are not executed. A `grep -rn 'ingpipe_ingpipe'` found all five and they were repaired. The lesson for a future prefix rename: the residual grep must search for the DOUBLED prefix as well as the old name, because a residual-name grep filtered on the new name cannot see it.
25. **Phase 3 verification (task 10), in full.** Against a throwaway `grants_scratch_db` with a `grants_scratch_ro`/`grants_scratch_maintainer` pair and the three served schemas: all three grants scripts applied cleanly and were a clean no-op on a second run (only `extension ... already exists, skipping` notices); `has_function_privilege` reports the read-only role can execute **none of the nine** mutating large-object functions; a `lo_truncate64(0, 1000000)` call as that role fails with `ERROR: permission denied for function lo_truncate64` (and `lo_from_bytea` likewise), while a plain `select 1` still succeeds, so the SELECT-only model is intact; `lo_get` remains executable, which is the intended read-side carve-out. All four assertions still raise on their violated preconditions — wrong database, a CREATEDB attribute, a `pg_read_all_data` membership, and a nonexistent role. The scratch database and both roles were dropped; `policy_db` was verified afterwards to still report `lo_truncate64` as executable by `mcp_ro_policy`, i.e. untouched, exactly as decision 10 requires.
26. **Phase 3 rationale change (9.2).** The removed RESIDUAL note is replaced by a statement of the whole mutating surface organised by ACT (create / open-for-writing / write / extend-or-shrink / destroy) rather than by an enumeration of what any audit reported, plus an explicit note on why the read-side functions are deliberately left granted. `lo_open` is revoked even though it also serves reads: nothing in the served schemas stores a large object, so there is no read use to preserve, and it is the descriptor `lowrite` and `lo_truncate*` both require.
27. **Task 12 results.** 936 tests pass from the workspace root and from a directory outside the repo (unchanged from the baseline in note 16); `ruff` and `mypy` clean; the 12.3 greps return only deliberate survivors (the new prefix-rationale prose in `MAINTAINING.packages.md`, `.acquisition_manifest.json`, and English prose). Each of the five wheels carries exactly its own top-level module plus its package data (`config/example.toml`, and the two `sql/*.sql` templates) and no sibling's modules. The collision was re-confirmed live: `ingestion-lib` (0.0.7, "Library for data ingestion") and `acquisition` (6.3) both resolve on PyPI, while all five `ingpipe-*` names return 404. Installing `dist/ingpipe_acquisition-...whl` alone against PyPI now FAILS loudly ("only ingpipe-acquisition==0.1.0 is available ... requirements are unsatisfiable") instead of silently pulling a stranger's library — that failure IS the fix; adding the local `ingpipe-lib` wheel makes it install, and its 172 tests pass in the scratch environment against the installed distribution. All thirteen console scripts (counted from the `[project.scripts]` blocks, matching the plan) return `--help` successfully from outside the repo, and both acquisition dry runs resolve their targets and exit 0, writing their logs under the new `logs/ingpipe_acquisition/` subdirectory.
